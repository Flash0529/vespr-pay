# Writing documentation

- **Start from the reader:** who are they, what do they already know, what are they trying to do? Say it in the first lines.
- **Pick one kind per page:** a tutorial (a guided first success), a how-to (steps for one task), a reference (complete, dry, accurate) or an explanation (why it works this way). Do not mix them.
- **README order:** what it is in one sentence, what it looks like (screenshot or output), install and run in the fewest commands, a minimal example, where to go next, licence. Every command must be copy-pasteable and tested by running it.
- **Be concrete:** real example values, real output, real error messages. Name the exact file, command and setting.
- **Keep it true:** read the code before describing it; date things that will age; do not describe features that do not exist (mark plans as plans).
- **Style:** short sentences, active voice, one idea per paragraph, headings that say what the section answers, American English for public text, no filler or hype.
- **Finish:** run the instructions from a clean state, fix what broke, and list what you could not verify.
